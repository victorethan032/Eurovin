# EuroVin — mise en service des paiements et de la gestion (Stripe)

Ordre à suivre, **toujours en mode test d'abord** (clés `sk_test_…`, cartes de test Stripe).

## 1. Base de données
1. Supabase → SQL Editor : exécuter `schema.sql`, puis `schema-paiements.sql`, puis `schema-rapport.sql`, puis **`schema-facturation.sql`** (mentions légales des factures, statut comptable, verrou d'immutabilité), puis **`schema-emails.sql`** (journal des e-mails, consentement marketing, désabonnement) ; puis **`schema-admin.sql`** (paramètres de l'exploitant), puis **`schema-admin-plus.sql`** (comptes d'administration, sessions, notes clients) ; tous rejouables.
   Dans Supabase → Settings → API, copier la clé **anon** dans `SUPABASE_ANON_KEY` (le site s'en sert pour la connexion) ; la clé service reste côté serveur.
2. Vérifier que les tables `credit_notes`, `stripe_events`, `support_tickets`, `report_errors`, `admin_audit` existent.

## 2. Stripe : moyens de paiement (toute l'Europe)
Dashboard → Paramètres → Moyens de paiement. Activer, selon ce que votre compte autorise :
carte (Visa, Mastercard, CB), Apple Pay, Google Pay, Link, PayPal, iDEAL (NL), Bancontact (BE), SEPA (prélèvement), EPS (AT), Przelewy24 (PL), BLIK (PL), Klarna, etc.
- Le code **n'impose aucune liste** : Checkout affiche automatiquement les moyens adaptés au pays et à la devise de l'acheteur.
- Chaque moyen peut demander une activation ou une vérification par Stripe : certains ne sont pas disponibles pour tous les comptes.
- Les paiements en euros uniquement pour l'instant : BLIK (zloty) n'apparaîtra pas tant qu'on ne vend pas en PLN.
- Les moyens « différés » (SEPA, virement) : le rapport n'est livré qu'une fois l'argent confirmé (événement `async_payment_succeeded`).

## 3. Stripe : TVA, factures, portail
- Activer **Stripe Tax** (Dashboard → Taxes) et renseigner votre adresse et vos numéros de TVA (guichet unique OSS si vous vendez dans plusieurs pays de l'UE). `STRIPE_TAX=1`.
- Activer le **portail client** (Dashboard → Paramètres → Facturation → Portail client) en autorisant la mise à jour des moyens de paiement : c'est ce que l'espace client ouvre.
- Codes promo : Dashboard → Produits → Coupons → créer un code promotionnel. Un code à 100 % crée une commande à 0 € (rapport livré, facture à 0 €).

## 4. Webhook
Dashboard → Développeurs → Webhooks → ajouter `https://VOTRE-DOMAINE/api/webhooks/stripe` avec ces événements :
`checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, **`checkout.session.expired`** (paiements abandonnés, pour la carte « ce qui ne se vend pas »),
`refund.created`, `refund.updated`, `refund.failed`,
`charge.dispute.created`, `charge.dispute.updated`, `charge.dispute.closed`.
Copier la clé de signature dans `STRIPE_WEBHOOK_SECRET`. En local : `stripe listen --forward-to localhost:3000/api/webhooks/stripe`.

## 5. Variables d'environnement
Copier `.env.example` en `.env`. `ADMIN_API_KEY` (32 caractères minimum) conditionne l'ouverture du back-office.

## 9. Site, rapport et PDF (v2)
- Le serveur sert lui-même le site (dossier `site/`, adresses `/report/…`, `/compte`, `/pro`, `/cgv`…) et `/config.js` (valeurs publiques uniquement). Un seul service à héberger (Render, Railway, Fly… : il faut un serveur Node qui tourne, pas des fonctions courtes).
- `POST /api/preview` (gratuit, lit la marque dans le VIN), `GET /api/checkout/status?session_id=…` (page « merci »), `GET /api/reports/:jeton` (rapport v2), `GET /api/reports/:jeton/pdf`.
- Les PDF (facture, avoir, rapport) utilisent `pdf-lib` (aucune dépendance native).
- Libellés d'options : fournisseur FR > `option_labels` (validés par vous) > glossaire intégré > libellé d'origine signalé. File de travail : `GET /api/admin/labels/untranslated`, validation : `PUT /api/admin/labels` `{brand, code, labelFr}`.
- Fournisseurs : `PROVIDER_ORDER` (options), `HISTORY_ORDER` (historique/sinistres, Premium), `RECALL_ORDER` (rappels). Les adaptateurs réels restent à écrire dans `providers.js` (contrats documentés en tête de fichier) ; sans eux, une rubrique est affichée « information non disponible », jamais vide ni inventée.
- Cotation : `VALUATION_ENABLED=0` au lancement.

## 9 bis. Factures conformes et Pennylane
**Factures.** Chaque facture conserve une copie figée du vendeur et de l'acheteur : numéro, dates (émission, prestation, échéance), vendeur (forme, capital, SIREN, RCS, TVA), acheteur (nom, adresse, SIREN, n° de TVA), nature de l'opération (prestation de services), lignes avec **PU HT, taux de TVA, total HT, TVA, TTC**, mention « acquittée », et pour les professionnels : pénalités de retard, indemnité de 40 €, escompte. Cas particuliers : autoliquidation (client UE avec n° de TVA), franchise en base (`SELLER_VAT_FRANCHISE=1`), TVA nulle sans justificatif (statut « à valider »). Le montant et le numéro d'une facture émise ne peuvent plus être modifiés (verrou en base).
**Achat de crédits (clients Pro).** La raison sociale et un SIRET valide sont obligatoires (Mon espace › Informations) : ils sont repris sur la facture. Sinon l'API répond `COMPANY_REQUIRED`.
**Pennylane.** Renseigner `PENNYLANE_API_TOKEN`. Chaque facture est envoyée (client, PDF, lignes avec code TVA) juste après le paiement, puis rattrapée par le cron `/api/jobs/sweep` en cas d'échec (délais croissants, 8 essais). Une panne Pennylane ne bloque jamais une commande. Clients particuliers : regroupés sous un seul client Pennylane « Clients particuliers » ; professionnels : un client par SIREN. Cas à décision humaine (TVA étrangère, autoliquidation…) : statut `needs_review`, rien n'est envoyé.
**Back-office.** `GET /api/admin/accounting?status=` (état), `POST /api/admin/accounting/retry {id}` (relance), `GET /api/admin/accounting/export?from=AAAA-MM-JJ&to=AAAA-MM-JJ` (CSV pour le comptable : factures + avoirs en négatif ; Excel, séparateur « ; »).
**Avoirs.** Par défaut non envoyés à Pennylane (ils figurent dans le CSV) ; `PENNYLANE_CREDIT_NOTES=1` active un envoi expérimental.

## 9 ter. E-mails de service, marketing et export mensuel
**Principe.** Deux flux séparés. *Service* (envoyés par Resend, toujours, sans publicité) : bienvenue à la création du compte (première visite de Mon espace), paiement reçu + facture PDF, rapport prêt + PDF, crédits ajoutés (pack), crédits débités et solde, alerte solde faible (`LOW_CREDITS_THRESHOLD`), remboursement + avoir PDF, retard de commande, rapport bientôt supprimé (7 jours avant), message support reçu / traité, modification du profil, compte Pro activé, ajustement de crédits par nos soins, facture Pro incomplète, suppression de compte, échec de paiement. *Marketing* : jamais envoyé par ce serveur ; liste des inscrits consentants à importer dans Brevo.
**Fiabilité.** Chaque e-mail a une clé unique (journal `email_log`) : un événement rejoué n'envoie rien de plus ; un échec Resend est tracé, ne bloque jamais la commande, et est rattrapé (3 essais, 8 pour le rapport). `GET /api/admin/emails?status=failed` liste les échecs.
**Consentement.** Case facultative, décochée, à l'inscription (et dans Mon espace › Informations). Preuve conservée (`consent_events` : date, origine). Désabonnement : lien `/desabonnement?t=…` (page de confirmation, action par POST), possible aussi en un clic ; `POST /api/webhooks/brevo` (en-tête `x-webhook-secret` = `BREVO_WEBHOOK_SECRET`) répercute les désabonnements et rebonds Brevo.
**Brevo.** `GET /api/admin/marketing/export` → CSV (`;`, UTF-8) : EMAIL, TYPE, ENTREPRISE, DATE_CONSENTEMENT, SOURCE_CONSENTEMENT, DATE_INSCRIPTION. À importer dans une liste Brevo ; les e-mails marketing doivent garder le lien de désabonnement Brevo.
**Export comptable mensuel.** `GET /api/admin/accounting/monthly?month=AAAA-MM[&part=detail]` : synthèse TVA par pays / régime / taux (factures − avoirs = net à déclarer) ou détail des pièces. Le cron (`/api/jobs/sweep`) envoie automatiquement le mois écoulé à `ADMIN_EMAIL` (+ `ACCOUNTANT_EMAIL`) à partir du 2 du mois, une seule fois ; `POST /api/admin/accounting/monthly/send {month}` le renvoie à la demande. Mois calendaires à l'heure de Paris.
**À faire côté Supabase.** Personnaliser en français les e-mails d'authentification (confirmation d'adresse, mot de passe oublié) : ils sont envoyés par Supabase, pas par ce serveur. Configurer SPF/DKIM/DMARC du domaine d'envoi chez Resend.

## 9 quater. Console d'administration (`/admin`)
Page web (même design que le site) qui remplace l'usage de l'API à la main : **Tableau de bord** (chiffre d'affaires net, TVA, alertes à traiter), **Commandes** (recherche, détail, facture, remboursement total ou partiel avec motif et double confirmation, renvoi du rapport, relance), **Clients** (fiche, ajustement de crédits, passage Pro), **Support** (réponse par e-mail, clôture, erreurs de rapport), **Libellés** (traduction des options inconnues), **Comptabilité** (export mensuel TVA par pays, export par période, état et relance Pennylane), **E-mails** (échecs, liste Brevo), **Paramètres**.
**Connexion :** on saisit `ADMIN_API_KEY` (gardée dans l'onglet seulement) et son prénom (journal des actions). Pour plus de sécurité, `ADMIN_IP_ALLOWLIST` rend `/admin` et l'API invisibles hors des adresses listées, ou placer le tout derrière un VPN.
**Profil de l'exploitant :** l'onglet Paramètres permet de saisir raison sociale, forme, capital, SIREN (contrôlé), RCS, adresse, TVA, e-mail : ces valeurs priment sur les variables `SELLER_*` et alimentent factures, avoirs et e-mails. **Tant que les mentions obligatoires sont incomplètes, la vente est suspendue** (`/api/checkout` répond 503) : jamais de facture incomplète.
**État de la configuration :** liste de contrôle oui/non (TVA automatique, webhook, fournisseur de données réel, HTTPS, cron, e-mail admin, Pennylane, comptable, Brevo, IP) ; aucun secret n'est affiché.
**Page profil client (Mon espace › Informations) :** coordonnées, facturation professionnelle (société, SIRET contrôlé en direct, n° de TVA, indicateur « prêt pour les factures Pro »), préférences e-mail.

## 9 quinquies. Modifier le site depuis l'administration (onglet « Site »)
Sans toucher au code, depuis `/admin` › **Site** : **bandeau d'annonce** (information ou attention), **maintenance** (bandeau rouge + aucune nouvelle commande : `/api/checkout` répond 503 `MAINTENANCE`), **prix** (Essentiel et Premium TTC, packs Pro HT), **textes de la page d'accueil**, **nom du site et e-mail de contact**, **valorisation** (activée/désactivée), **pages légales** (éditeur avec aperçu, « préremplir avec le texte d'origine », « revenir au texte d'origine ») et **FAQ** (ajouter, réordonner, supprimer). La version précédente est conservée : bouton « Restaurer la version précédente ». Tout est stocké dans `app_settings` (clés `site` et `site_prev`, aucune nouvelle table) et lu par le site via `GET /api/site` (public, sans donnée sensible).
**Prix :** le serveur applique le nouveau prix aux **prochains paiements Stripe uniquement** (les prix sont envoyés à Checkout à chaque commande, rien à modifier dans Stripe). Les commandes, factures et avoirs déjà émis ne changent pas. Un changement de prix exige une **confirmation explicite** (second clic sur Enregistrer) et le serveur refuse les incohérences (Premium moins cher qu'Essentiel, pack plus gros plus cher au crédit, prix hors bornes). Le prix affiché sur le site vient de la même configuration que le prix facturé.
**Textes :** texte simple uniquement (`## Titre`, `- puce`, `**gras**`, `[texte](https://…)`, ligne vide = paragraphe). Aucun HTML n'est interprété : tout est échappé avant mise en forme et seuls les liens `https:` et `mailto:` sont acceptés. **Les pages légales restent sous votre responsabilité** : faites relire tout texte modifié par un juriste. Une page laissée vide garde le texte d'origine, qui contient des passages « [à compléter] ».
**Délai :** visible immédiatement sur l'instance qui enregistre ; les autres instances relisent la configuration toutes les 60 s.
**Dans la démo :** le lien **Admin** (en haut) ouvre la même console sur des données fictives (mot de passe `demo-admin`, uniquement un garde-fou de démonstration). Les changements de bandeau, prix, textes, pages et FAQ s'appliquent en direct au site de démonstration, avec la vraie validation du serveur.

## 9 sexies. Administration avancée (comptes, graphiques, promo, e-mails, brouillons)
- **Comptes personnels et rôles** (onglet *Équipe*, propriétaire seulement) : chacun a son e-mail, son mot de passe (12 caractères minimum, stocké haché *scrypt*) et sa double authentification (code à 6 chiffres, saisie manuelle de la clé dans l'application : pas de QR code). Rôles : **propriétaire** (tout), **lecture seule** (consultation, sans export de données personnelles ni équipe), **comptable** (commandes et comptabilité). Mot de passe provisoire affiché une seule fois, à changer à la première connexion. 5 échecs = verrouillage 15 min + e-mail d'alerte ; chaque connexion envoie une alerte ; toutes les actions sont tracées au nom de la personne. La **clé de secours** (`ADMIN_API_KEY`) reste le compte propriétaire d'urgence.
- **Graphiques et pilotage** (tableau de bord) : chiffre d'affaires par jour, répartition Essentiel/Premium et types de commande, taux de remboursement, **qualité par marque et par fournisseur**, **marge estimée** (renseignez vos coûts dans *Paramètres* : ce sont des estimations).
- **Ce qui se vend / ne se vend pas** (bouton sur la carte du même nom) : les 5 offres (Essentiel, Premium, packs 10/30/100) classées de la moins vendue à la plus vendue, **y compris celles sans aucune vente** (étiquette « Aucune vente »), avec les ventes, les remboursements et les **paiements abandonnés** (taux d'abandon = abandons / paiements commencés). Les abandons viennent de l'événement Stripe `checkout.session.expired` (à ajouter au webhook, § 4) : une session n'expire qu'après 24 h par défaut et le suivi ne compte qu'à partir de son activation ; il n'enregistre que le type d'offre et la date (aucune donnée personnelle, conservé 13 mois, table `abandoned_checkouts`).
- **Marge réelle** (bouton *Estimée / Réelle* sur la carte de marge) : CA net HT − **frais Stripe réellement prélevés** − **charges que vous saisissez** (*Paramètres › Charges réelles*, montants HT : fournisseur de données, outils, hébergement, publicité…). Les frais réels sont relevés auprès de Stripe à la réception du paiement (colonne `orders.stripe_fee_cents`, best-effort : un paiement SEPA différé ou une erreur Stripe laisse la valeur vide) ; pour les commandes sans frais relevé, la carte utilise vos taux et l'indique (« en partie estimés »). Sans charges saisies, la marge réelle est surévaluée : elle ne connaît pas vos coûts de données tant que vous ne les saisissez pas.
- **Codes promo** (onglet *Codes promo*) : créés dans Stripe (pourcentage ou montant, nombre d'utilisations, expiration, désactivation). La facture indique le prix réellement payé, remise déduite. `ALLOW_PROMO_CODES=0` retire le champ.
- **Textes des e-mails de service** : objet et paragraphe d'introduction modifiables avec aperçu ; le contenu légal reste fixe. Pas de promotion dans ces e-mails (réservé au marketing avec consentement).
- **Brouillon, aperçu privé et publication planifiée** du contenu du site (onglet *Site*).
- **Résumé quotidien** des points à traiter envoyé à `ADMIN_EMAIL`, et **publication planifiée** : ils s'exécutent quand `/api/jobs/sweep` est appelé (tâche planifiée, au moins toutes les heures).
- **Recherche globale** (e-mail, VIN, n° de facture ou d'avoir, id de commande), **notes privées** sur les clients, **import de traductions en lot** (`MARQUE;CODE;Libellé`).
- **Comparaison avec la période précédente** (flèches ▲▼ en %), **objectif de CA du mois** (barre, projection de fin de mois ; réglage dans la carte), **entonnoir de conversion** (recherche → paiement → rapport ouvert) et **marques recherchées sans achat**. Les compteurs sont anonymes (table `funnel_daily`, fonction `bump_funnel`, purgés après 400 jours) et comptent les recherches brutes, VIN répétés et rechargements du rapport compris : l'étape « ouvert » peut donc dépasser 100 % de la précédente.
- **Clients Pro : usage des crédits** (jamais utilisés, endormis, bientôt épuisés, épuisés), **TVA et encaissements** avec **récapitulatif mensuel CSV/PDF** (estimations : le comptable reste la référence) et **santé technique** (délais de génération, erreurs).
- À exécuter : `schema-admin-plus.sql`. Dans la démo : comptes d'essai `proprietaire@exemple.fr`, `lecteur@exemple.fr`, `compta@exemple.fr` (mot de passe `demo-admin`, code 2FA du comptable `123456`).

## 9 septies. Utilisation sur téléphone
Le site, le rapport, le paiement, l'espace client, Pro et toute la console d'administration s'adaptent aux écrans de 320 à 430 px (et au-delà) : mêmes écrans et mêmes fonctions, seule la mise en page change. Menu horizontal défilant, champs à 16 px (pas de zoom automatique sur iPhone), boutons d'au moins 44 px, zones de sécurité des iPhone respectées, effets de survol désactivés au toucher. Dans la console, chaque tableau devient une liste de cartes avec le nom de la colonne devant chaque valeur (c'est `admin.js` qui ajoute ces libellés), et les 12 onglets défilent horizontalement en gardant l'onglet actif visible. Les fichiers concernés sont `site/style.css` et `site/admin.css` (blocs « Adaptation téléphone » en fin de fichier). **Parcours client pensé pour le téléphone** (`site/mobile.js`, actif seulement sur écran étroit ; sur ordinateur rien ne change) :
- **Barre d'onglets en bas** (Vérifier, Pro, À propos, Aide, Compte/Mon espace), comme une application ; elle se range quand le clavier s'ouvre.
- **Saisie du VIN** : majuscules automatiques, espaces et tirets supprimés, compteur « 12 / 17 », lettres I, O, Q signalées, bouton **Coller** (extrait un VIN d'un texte collé) et bouton **Scanner** (caméra, codes-barres Code 39/128, DataMatrix et QR) affiché seulement si le navigateur sait lire les codes-barres (en pratique Chrome sur Android ; absent sur iPhone, où l'on saisit ou colle).
- **Bouton « Continuer · 12,99 € TTC »** collé en bas de l'aperçu, avec le prix du rapport choisi. Le bouton de commande finale reste dans la page, après les cases à cocher, avec son libellé légal inchangé.
- **Onglets du rapport collés** en haut pendant le défilement, **fenêtres en feuilles** qui montent du bas (fermeture en touchant le fond), bouton **Partager…** natif (feuille de partage du téléphone) en plus de la copie du lien.
- **Application installable** : `manifest.webmanifest`, icônes, couleur de thème, `sw.js`. Le service worker ne met en cache que la coquille du site ; **jamais** les appels `/api/`, les rapports ni les paiements. Hors connexion, un bandeau l'indique. Sur Android, un lien « Installer l'application » apparaît en bas de page ; sur iPhone : Partager puis « Sur l'écran d'accueil ».

À vérifier sur de vrais téléphones (iPhone Safari, Android Chrome) : le test automatique (`npm run test:mobile`) émule un écran tactile dans Chromium, pas un vrai appareil.

## 9 octies. Aperçu enrichi, guide du VIN illustré, alerte rappel
- **Aperçu gratuit** : en plus de la marque, il affiche le **pays du constructeur** (2 premiers caractères du VIN) et une **année modèle indicative** (10e caractère), lus dans le VIN sans consulter de base de données (`site/vinfacts.js`, partagé par le serveur et la démonstration). Le pays est celui où le constructeur est **enregistré**, pas forcément celui de l'usine ; l'année peut être double (« 2016 ou 1986 ») et n'est pas un code d'année pour tous les véhicules européens : l'aperçu le dit. Les préfixes dont l'attribution est incertaine ne sont pas affichés (rien n'est inventé).
- **Guide « Où trouver mon VIN ? »** : quatre onglets avec schémas (carte grise champ E, bas du pare-brise côté conducteur, montant de porte, plaque sous le capot) et l'anatomie d'un VIN. Clavier et lecteurs d'écran pris en charge ; schémas dessinés en SVG (aucune image à héberger). Les emplacements sont ceux courants sur les voitures : à confirmer sur quelques modèles.
- **Alerte rappel** (facultative, **désactivée par défaut**) : sur la fiche technique du rapport, le client coche une case pour être prévenu par e-mail d'une nouvelle campagne de rappel pour son VIN. Fonctionnement : le consentement est enregistré (date) ; au premier passage de `/api/jobs/sweep` on mémorise les campagnes existantes **sans envoyer d'e-mail** ; ensuite chaque alerte est contrôlée tous les 7 jours (`RECALL_INTERVAL_DAYS`) et un seul e-mail part pour chaque nouvelle campagne (dédoublonné). Source indisponible = aucune alerte, nouvel essai le lendemain. Chaque e-mail contient un lien d'arrêt en un clic (la page de confirmation n'a aucun effet tant qu'on ne clique pas, comme pour le désabonnement) et les en-têtes « List-Unsubscribe ». Arrêt automatique après 24 mois, suppression avec le compte, plafond de 50 alertes actives par adresse.
  - **À faire pour l'activer** : exécuter `schema-rappels.sql`, renseigner `RECALL_ORDER` (un fournisseur de rappels dont l'adaptateur est écrit : aujourd'hui seul `mock` existe pour les tests, `automotivapi` est un gabarit à compléter) puis `RECALL_ALERTS=1`. **Coût** : une consultation de la source par alerte active et par semaine ; la carte « Alertes rappel » du tableau de bord donne le nombre mensuel estimé. Le texte de l'e-mail est modifiable (onglet *Textes e-mails*). Ajoutez la mention dans votre politique de confidentialité (un paragraphe est prévu dans `legal.js`, à faire valider).

## 11. Ce qui n'est PAS encore vérifié
- **Alerte rappel** : testée avec une fausse source de rappels ; aucun fournisseur réel n'est branché, donc ni le format réel de leurs données (identifiants de campagne stables ?) ni leur tarif ne sont vérifiés. Si un fournisseur ne donne pas d'identifiant stable, l'alerte se base sur le titre et la date, ce qui peut déclencher une alerte superflue si le fournisseur reformule un titre.
- **Aperçu enrichi et guide du VIN** : tables de pays et de codes d'année écrites d'après la norme ISO 3779 et jamais confrontées à une base de VIN réels ; schémas du guide non validés auprès de vrais utilisateurs.
- **Scanner de VIN, bouton Coller, installation, partage natif** : écrits d'après les API des navigateurs mais jamais essayés sur un vrai téléphone ; la lecture d'un vrai code-barres de pare-brise dépend de la netteté et de l'éclairage. Le service worker n'a pas été exécuté par un vrai navigateur sur HTTPS.
- **Téléphone** : rendu validé en émulation (Chromium, 320 à 430 px), jamais sur un vrai iPhone ni un vrai Android (clavier virtuel, barre d'adresse qui se réduit, mode sombre, encoche).
- Aucun appel réel à Stripe, Supabase, Resend, ni aux fournisseurs de données (npm est bloqué dans notre environnement de travail). Faites `npm install && npm test` chez vous, puis un parcours complet en mode test Stripe.
- Le vrai `express`, `helmet` (politique CSP) et `express-rate-limit` n'ont pas été exécutés : vérifier dans le navigateur (console) qu'aucune ressource n'est bloquée.
- Le schéma SQL (`schema*.sql`) n'a pas été exécuté sur un vrai Postgres : le jouer sur un projet Supabase de test et corriger les éventuelles erreurs.
- **Invendus** : l'événement `checkout.session.expired` n'a jamais été reçu du vrai Stripe ; à vérifier sur une session de test laissée expirer (la durée d'expiration d'une session Checkout se règle côté Stripe, minimum 30 minutes).
- **Marge réelle** : la lecture des frais (`paymentIntents.retrieve` avec `latest_charge.balance_transaction`) n'a jamais été essayée contre le vrai Stripe ; vérifier sur un paiement test que `stripe_fee_cents` se remplit, et que les frais en devise étrangère ou les paiements différés se comportent comme prévu. Les frais Stripe ne sont en général pas restitués lors d'un remboursement : ils restent comptés.
- **Administration avancée** : jamais exécutée contre le vrai Stripe (codes promo, `allow_promotion_codes`, facture au prix net après remise), ni contre un vrai Postgres (`schema-admin-plus.sql`). Le code TOTP est conforme à la RFC 6238 mais n'a pas été essayé avec une vraie application d'authentification (saisie manuelle de la clé, pas de QR code). Le résumé quotidien et la publication planifiée dépendent de l'appel régulier de `/api/jobs/sweep`. Les coûts/marge sont des estimations. Les accès par rôle ne remplacent pas une revue de sécurité.
- Noms d'événements et options Stripe à confirmer dans la version d'API de votre compte.
- Les frais de traitement Stripe ne sont en général pas restitués lors d'un remboursement : à intégrer dans vos marges.
- **Pennylane** : les noms de champs, les codes de TVA (`FR_200`…), le traitement des avoirs et le regroupement des particuliers sous un client unique viennent de la documentation publique et n'ont jamais été testés contre le vrai Pennylane : à essayer avec votre compte (ou un bac à sable) et à valider avec votre comptable.
